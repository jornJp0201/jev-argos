# アダプター仕様 (他の言語で実装する人向け)

jev-argos の判定サーバーは gRPC (`proto/signal.proto`) でアダプターとやり取りします。
**gRPC に対応している言語なら、この文書に従ってアダプターを書けば Node.js 版・Go 版と同じように検知と遮断ができます。**

公式のアダプターは次の 2 つで、どちらもこの仕様の実装例です。迷ったらコードを参照してください。

| 言語 | 場所 |
| --- | --- |
| Node.js | [packages/adapter-node/src](../packages/adapter-node/src) |
| Go | [pkg/client](../pkg/client) |

## 1. 対象になる言語・実行環境

条件は次の 2 つです。

1. その言語の gRPC 実装で、**単発の呼び出し**と**サーバー側のストリーミング**が使えること
2. **プロセスが常駐していること** (遮断リストのストリームを張り続けるため)

| 言語 | 判定 | 補足 |
| --- | --- | --- |
| Java / Kotlin, C#, Python, Ruby, C++, Dart, Swift | 使える | 公式の gRPC 実装がある |
| Rust | 使える | `tonic` を使う |
| PHP | 条件付き | PHP-FPM はリクエストごとにプロセスが終わるため、遮断リストを購読できない。RoadRunner / Swoole などの常駐環境か、購読を受け持つサイドカーが必要 |

送信だけ (検知だけ) なら、gRPC を使わずに HTTP の `POST /api/signals` (JSON、送信専用トークン `JEV_ARGOS_INGEST_TOKEN`) でも送れます。
ただし HTTP で遮断リストを取るには管理トークンが必要で、BFF に持たせるべきではないため、**遮断まで行うなら gRPC を使ってください**。

コードの生成は各言語の `protoc` プラグインで行います。

```bash
# 例: Python
python -m grpc_tools.protoc -I proto --python_out=. --grpc_python_out=. proto/signal.proto
```

## 2. 全体の構成と規模の目安

アダプターは次の 4 つの部品でできています。

```
  リクエスト ──> [ 組み込み (6章) ] ──> アプリのハンドラー
                   │   ▲
     観測結果 ──────┘   │ 遮断中か (手元のコピーを見るだけ)
                   ▼   │
  [ シグナルの組み立て (3章) ]   [ BlocklistWatcher (5章) ] <── WatchBlocklist (ストリーム)
                   │
                   ▼
  [ Reporter (4章) ] ── ReportSignal (非同期) ──> jev-argos-server
```

| 部品 | 行数の目安 (テストを除く) |
| --- | --- |
| シグナルの組み立て | 50〜80 行 |
| Reporter (送信) | 100〜150 行 |
| BlocklistWatcher (遮断リストの購読) | 70〜100 行 |
| gRPC インターセプター | 60〜100 行 |
| HTTP ミドルウェア (フレームワーク 1 つにつき、任意) | 80〜120 行 |
| **合計** | **gRPC だけなら 300〜450 行、HTTP も入れると 400〜600 行** |

参考: Node.js 版は約 910 行 (フレームワーク 3 つ分を含む)、Go 版は約 570 行です。

## 3. シグナルの組み立て

1 回のリクエスト (RPC) につき `SecuritySignal` を 1 件作ります。フィールドの定義は [proto/signal.proto](../proto/signal.proto) にあります。

### 3.1 フィールドに入れる値

| フィールド | 入れる値 | 判定に使うか |
| --- | --- | --- |
| `signal_id` | UUID | |
| `timestamp` | ISO 8601 (例: `2026-11-16T09:00:00.000Z`) | |
| `source_service` | 送信元のサービス名 (例: `main-bff`)。利用者が設定する | |
| `user_context.client_ip` | クライアント IP (3.3 節) | **使う** (送信元ごとの集計の単位) |
| `user_context.user_id` / `user_role` | 認証済みの利用者 ID と役割。取り出し方は利用者が設定する。分からなければ空 | |
| `user_context.user_agent` | `user-agent` ヘッダー | |
| `user_context.session_hash` | 3.4 節 | |
| `request_context.protocol` | `"grpc"` または `"http"` | |
| `request_context.method` | 3.2 節 | **使う** |
| `request_context.metadata_masked` | 利用者が指定したヘッダーだけ (3.4 節)。既定は空 | |
| `request_context.payload_summary` | 空でよい | |
| `response_context.status_code` | **gRPC のステータスコード** (3.5 節) | **使う** |
| `response_context.error_code` | HTTP の場合は 400 以上のステータスを文字列で (例: `"403"`)。それ以外は空 | |
| `response_context.error_message` | 既定は空。利用者が有効にした場合のみ、失敗時の詳細を先頭 256 文字まで | |
| `response_context.latency_ms` | 処理時間 (ミリ秒、整数) | **使う** |
| `trace_id` | `x-trace-id` → `x-request-id` → `traceparent` の順で最初に見つかった値 | |
| `sample_rate` | 正常な応答を間引いて送ったときの割合 (4 章の「間引き」)。間引いていなければ 0 (未指定) | **使う** (1/sample_rate 件ぶんとして数える) |

### 3.2 `method` (最も間違えやすい)

Jev は「5 分間に権限エラーを受けた **API の種類数**」で権限の探索を見つけます。
そのため、`method` は **同じ API なら常に同じ文字列** にしなければなりません。

| 種類 | 入れる値 | 例 |
| --- | --- | --- |
| gRPC | フルメソッド名 | `/user.UserService/GetUser` |
| HTTP | `大文字のメソッド + 半角スペース + ルートのパターン` | `GET /users/:id` |
| HTTP でどのルートにも合わない | `大文字のメソッド + " (unmatched)"` | `GET (unmatched)` |

- HTTP では**実際の URL を入れないでください**。`/users/1` と `/users/2` が別の API として数えられ、ID などの個人情報も送ってしまいます。
- パターンの書き方 (`:id` / `{id}` / `[id]`) はフレームワークのものをそのまま使ってかまいません。

### 3.3 クライアント IP

| 状況 | 取り方 |
| --- | --- |
| 既定 | TCP の接続元アドレス |
| 信頼できるプロキシ (ロードバランサーなど) の背後にある場合 | `x-forwarded-for` の先頭 → `x-real-ip` → 接続元アドレス の順 |
| gRPC クライアント側 (BFF がバックエンドを呼ぶ側) のインターセプター | 送信メタデータの `x-forwarded-for` → `x-real-ip` (BFF 自身が付けた値なので常に信頼する) |

- プロキシのヘッダーを信頼するかどうかは**設定にし、既定は信頼しない**こと。直接公開されたサーバーで信頼すると、攻撃者がヘッダーで IP を偽って判定を逃れられます。
- `::ffff:1.2.3.4` (IPv4-mapped IPv6) は `1.2.3.4` に直してください。遮断リストの IP と一致させるためです。

### 3.4 機密情報の扱い

- `session_hash`: `authorization` (なければ `cookie`) の値を `SHA-256(salt + 値)` でハッシュし、16 進数の先頭 32 文字を入れる。ソルトは利用者が設定できるようにする。トークン自体は送らない。値が無ければ空。HTTP では空でもよい
- `metadata_masked`: 利用者が指定したキーだけを入れる。キー名が `/authorization|cookie|token|secret|password|api[-_]?key/i` に当てはまる場合は、値を `***` にする。`-bin` で終わるキー (バイナリ) は送らない

### 3.5 ステータスコード

`status_code` には **gRPC のステータスコード** を入れます。gRPC ならそのまま、HTTP なら次の表で変換します。

| HTTP | gRPC |
| --- | --- |
| 400 未満 | 0 `OK` |
| 400 | 3 `INVALID_ARGUMENT` |
| 401 | 16 `UNAUTHENTICATED` |
| **403** | **7 `PERMISSION_DENIED`** (権限の探索の検知に使う) |
| 404 | 5 `NOT_FOUND` |
| 408, 504 | 4 `DEADLINE_EXCEEDED` |
| 409 | 6 `ALREADY_EXISTS` |
| 429 | 8 `RESOURCE_EXHAUSTED` |
| 501 | 12 `UNIMPLEMENTED` |
| 502, 503 | 14 `UNAVAILABLE` |
| 上記以外の 4xx | 9 `FAILED_PRECONDITION` |
| 上記以外の 5xx | 13 `INTERNAL` |

## 4. 送信 (Reporter)

**最も大事な決まり: 送信はアプリの処理を待たせず、アプリに例外を投げない。** 判定サーバーが止まっていても、アプリは普段どおり動かなければなりません。

| 項目 | 決まり |
| --- | --- |
| 呼び出し | `report(signal)` はキューに入れて**すぐに戻る**。送信はバックグラウンド (スレッド・イベントループの次のターンなど) で行う |
| RPC | `SignalService.ReportSignal` |
| タイムアウト | 1 件あたり既定 500 ms |
| 上限 | 送信中と送信待ちの合計が上限 (既定は Node.js 版 1000 件、Go 版 10000 件) に達したら、新しいシグナルは**捨てる**。待たせない・ためすぎない |
| 失敗 | 送信の失敗・タイムアウトは数えるだけで、アプリには伝えない。再送はしない |
| 例外 | シグナルの組み立てや利用者のコールバックで起きた例外も含め、すべて握りつぶす |
| 終了 | `close()` で新しい受付を止め、送信中のものを送り切ってから接続を閉じる |
| 統計 (推奨) | 送信できた件数・失敗した件数・捨てた件数を見られるようにする |
| 接続 | 既定は平文。TLS などの認証情報を利用者が指定できるようにする |

### バッチ送信 (任意)

アクセスが多い環境向けに、`SignalService.StreamSignals` でまとめて送る方式も使えます。

- 既定では 50 件たまるか、100 ms たつごとに 1 本のストリームで送る
- 応答の `immediate_action_level` はバッチ内の最大値になる
- 1 本のストリームの中に不正なシグナルが混ざっても、サーバーはそれを読み飛ばして残りを処理する

### 間引き (任意)

送る量を減らすため、正常な応答を一部だけ送る方式も使えます。**既定は全件送る**とし、利用者が割合 (`rate`) を指定したときだけ有効にします。

- エラー (`status_code != 0`) はすべて送る。サーバーの攻撃の判定はエラーだけから数えるため、判定は変わらない
- 遅い応答は必ず送る。API (`method`) ごとに手元で正常な応答の処理時間の平均 (EWMA、α = 0.1) を持ち、その 2 倍を超えた応答 (または利用者が指定した処理時間を超えた応答) が対象。初めて見る API の最初の応答も送る
- それ以外の正常な応答は `rate` の確率で送り、送ったシグナルの `sample_rate` に `rate` を入れる。必ず送ったシグナルには入れない
- 手元で平均を持つ API の数には上限を設ける (Go 版・Node.js 版は 1 万)
- 間引いた件数を統計で見られるようにする (推奨)

サーバーは `sample_rate` の付いたシグナルを 1/sample_rate 件ぶん (最大 100 件ぶん) として、レイテンシの基準値とダッシュボードの件数に反映します。
`sample_rate` を付けずに間引くと、遅い応答の割合が実際より多く見え、基準値が高くずれて処理時間の急増を見逃します。

### 応答

`ReportResponse.immediate_action_level` は、そのシグナルで決まった Level (1〜4) です。
コールバックで利用者に渡してもよいですが、**遮断は応答ではなく 5 章の遮断リストで行ってください** (遮断は複数台に共有され、期限もあるため)。

## 5. 遮断リストの購読 (BlocklistWatcher)

`ControlService.WatchBlocklist` を購読して、遮断中の送信元の一覧を手元に持ちます。
遮断中かどうかは手元のコピーだけで判定し、**リクエストのたびに通信してはいけません**。

### 5.1 受け取るイベント

| `kind` | 受け取ったときの処理 |
| --- | --- |
| `SNAPSHOT` | 手元の一覧を**全部消して**、`entries` に置き換える。接続直後に必ず 1 回届く |
| `ADDED` | `entries` を追加する。同じ対象 (`target_type` + `target`) があれば上書き |
| `REMOVED` | `entries` を一覧から消す |

- 対象のキーは `target_type` と `target` の組です。いまの `target_type` は `"ip"` だけです。
- 未知の `target_type` が来ても無視してかまいません (将来の拡張用)。

### 5.2 期限

- `expires_at_unix_ms` が 0 より大きく、現在時刻以前になったものは**遮断していないものとして扱う** (サーバーからの `REMOVED` を待たない)
- 0 は無期限

### 5.3 切断と再接続

| 項目 | 決まり |
| --- | --- |
| 再接続 | ストリームがエラーまたは終了で切れたら、自動で再接続する |
| 待ち時間 | 1 秒から倍々に延ばし、上限は既定 30 秒。イベントを 1 件受け取ったら 1 秒に戻す |
| 切れている間 | **最後に受け取った一覧で判定を続ける** (期限切れのものは 5.2 節のとおり外す) |
| 再接続したとき | 最初に `SNAPSHOT` が届くので、それで一覧を置き換える |
| 準備ができたか | 最初の `SNAPSHOT` を受け取ったかどうかを、利用者が確認できるようにする (推奨) |
| 終了 | `close()` でストリームを取り消す。取り消しによる `CANCELLED` はエラーとして扱わない |

### 5.4 判定

`isBlocked(ip)` は、3.3 節と同じ方法で正規化した IP が一覧にあり、期限内なら true を返します。

## 6. 組み込み (インターセプター / ミドルウェア)

### 6.1 gRPC サーバー (BFF / バックエンドが gRPC を提供する側)

1. RPC の開始時に時刻を記録し、接続元アドレスを取る
2. 受信メタデータを受け取ったら IP を決め (3.3 節)、**遮断中ならアプリのハンドラーを呼ばずに `PERMISSION_DENIED` (`"blocked by jev-argos"`) で拒否する**。拒否した RPC もシグナルとして送る
3. ハンドラーが終わったら、ステータスコードと処理時間でシグナルを組み立てて `report()` する
4. クライアントの切断や期限切れで終わった場合は、`CANCELLED` として送る
5. 1 回の RPC につきシグナルは**ちょうど 1 件**にする (二重に送らない)

### 6.2 gRPC クライアント (BFF がバックエンドの gRPC を呼ぶ側)

- 呼び出しの開始から、ステータスを受け取るまでを測る
- IP は送信メタデータの `x-forwarded-for` / `x-real-ip` から取る (3.3 節)
- 遮断はしない (遮断はリクエストを受ける側で行う)

### 6.3 HTTP ミドルウェア (任意)

1. リクエストの開始時に時刻を記録し、IP を決める
2. 遮断中なら、アプリのハンドラーを呼ばずに **403** と `{"error":"forbidden"}` を返す (応答の内容は利用者が変えられるようにする)。拒否したリクエストもシグナルとして送る
3. 応答を返し終えたら、ルートのパターン (3.2 節)・HTTP ステータス (3.5 節で変換)・処理時間でシグナルを組み立てて `report()` する

### 6.4 共通

- ミドルウェアやインターセプターは、**アプリのルートより前** (最初) に登録するよう README に書く
- シグナルの組み立てや送信で起きた例外は握りつぶす。監視の失敗でアプリのリクエストを失敗させない

## 7. チェックリスト

実装できたら、次を確かめてください。テスト用の判定サーバーは `go run ./cmd/jev-argos-server` で起動できます。

- [ ] 判定サーバーを止めた状態でも、アプリの応答時間が変わらず、エラーも出ない
- [ ] 403 を返すルートで、`status_code` が 7 になっている
- [ ] HTTP の `method` が `GET /users/:id` のようにパターンになっていて、実際の URL が入っていない
- [ ] 存在しないパスで `GET (unmatched)` になる
- [ ] プロキシのヘッダーを信頼しない設定 (既定) で、`x-forwarded-for` を偽っても IP が変わらない
- [ ] 存在しないパスに 1 分間で 30 回アクセスすると、サーバーのログに `level=3 downgraded=true` が出る
- [ ] 管理 API で IP を遮断 (`POST /api/blocklist`) すると、その IP からのリクエストがすぐに拒否される (403 / `PERMISSION_DENIED`)
- [ ] 解除 (`DELETE /api/blocklist?target=...`) すると、すぐに通るようになる
- [ ] 判定サーバーを再起動しても、自動で再接続して遮断リストが元に戻る
- [ ] 遮断の期限が過ぎると、サーバーからの通知を待たずに通るようになる
