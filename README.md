# jev-argos

[![CI](https://github.com/jornJp0201/jev-argos/actions/workflows/ci.yml/badge.svg)](https://github.com/jornJp0201/jev-argos/actions/workflows/ci.yml)

**Web サービスの BFF / バックエンドに組み込む、攻撃の検知と遮断のためのライブラリ。**

アプリにアダプター (ミドルウェア) を組み込むと、リクエストの情報が判定サーバーに送られ、送信元ごとの直近の振る舞いから攻撃を見つけます。
危険と確信できる送信元はその場で遮断し、確信が持てないものは人間の承認を待ちます。

| 機能 | 内容 |
| --- | --- |
| **検知** | 権限の探索 (管理 API を片っ端から試す)・エラーの集中・処理時間の急増を、送信元ごとの直近の振る舞いから見つける |
| **自動遮断** | 危険と確信できる送信元を、その場で一定時間 (既定 15 分) 403 で拒否する |
| **人間が最終判断** | 確信が持てないものは自動で遮断せず、管理者の承認を待つ。正常なユーザーを誤って締め出さないため |
| **LLM 分析** | 怪しい送信元について「何が起きているか」「どう対応すべきか」を LLM がまとめる (既定はローカルの Ollama、API キー不要) |
| **通知** | 要注意の送信元を Slack や Webhook に知らせる |

**アプリを遅くしません。** アダプターは応答を返した後に情報を送るだけで、判定サーバーが止まっていてもアプリには影響しません。

## しくみ

jev-argos は 2 つの部品でできています。

| 部品 | どこで動くか | 役割 |
| --- | --- | --- |
| **アダプター** | あなたの BFF の中 (ライブラリ) | リクエストの情報 (送信元 IP・API・ステータス・処理時間) を送り、遮断中の送信元を拒否する。Node.js 版 `@jornjp/adapter-node`、Go 版 `pkg/client` |
| **判定サーバー** `jev-argos-server` | 別プロセス (Docker / `go run`) | 採点・遮断・承認キュー・LLM 分析・通知を行う。Go のライブラリ (`pkg/`) として自分のサーバーに組み込むこともできる |

```
  あなたのアプリ                               jev-argos-server
  ==============                               ================

  [ BFF (Node.js / Go) ]
    + adapter  --- request info (async) --->   score each request (Jev)  ->  Level 1-4
               <-- blocked IPs -------------     Level 4    : block automatically
                                                 Level 3-4  : notify (Slack / Webhook)
                                                 Level 3    : approval queue
                                                 Level 2-4  : LLM analysis, decision log
```

判定エンジン **Jev** は、1 件のリクエストだけでなく同じ送信元の直近の振る舞い (1 分間のエラー数・5 分間に権限エラーを受けた API の種類数・普段に対する処理時間の比) を合わせて採点し、
**リスクスコア S** (0.0〜4.0) と **確信度 C** (0.0〜1.0) を出します。

| Level | 条件 | 対応 |
| --- | --- | --- |
| **1** 正常 | S < 1.5 | 何もしない。大半のリクエストはここ |
| **2** 不審 | 1.5 ≤ S < 2.5 | 判定ログに残し、LLM が分析する |
| **3** 攻撃の疑い | 2.5 ≤ S < 3.5、**または** S ≥ 3.5 で C < 0.8 | 「IP の一時遮断」を承認キューに提案し、通知する。管理者が承認すると遮断する |
| **4** 危険 | S ≥ 3.5 **かつ** C ≥ 0.8 | その場で自動遮断し (既定 15 分)、通知する |

- スコアが危険域でも確信度が足りなければ、自動遮断せず人間の判断 (Level 3) に回します。
- LLM が提案した対処や、取り消せない操作 (アカウント削除など) も、管理者が承認するまで実行されません。
- 閾値は暫定の初期値で、環境変数で変更できます。判定の詳細は [判定サーバーの README](cmd/jev-argos-server/README.md#判定のルール) を参照。

Redis・PostgreSQL・LLM・Slack はすべて**任意**です。何も用意しなくても判定と遮断は動きます
(LLM 分析は既定で Ollama を使うため、Ollama が無いと起動時に警告が出ます。不要なら `JEV_ARGOS_LLM_PROVIDER=none`)。

## 5 分で試す

判定サーバー・Redis・PostgreSQL・ダッシュボードを Docker Compose でまとめて起動し、**テスト用 BFF** に攻撃のようなリクエストを送って、遮断されるまでを確かめます。

> **本体とテスト用の区別**
> - 本体: 判定サーバー (`cmd/`, `pkg/`)、アダプター (`packages/adapter-node`, `pkg/client`)、ダッシュボード (`packages/dashboard`)
> - テスト用: `examples/test-bff` のみ。認証はダミーなので**本番では使わないでください**

```bash
# 1. 一式を起動する
export JEV_ARGOS_ADMIN_TOKEN=$(openssl rand -hex 16)   # 管理 API のトークン (Docker Compose では必須)
docker compose up --build

# 2. 別のターミナルで、テスト用 BFF を起動する (http://localhost:4000)
corepack enable && pnpm install && pnpm --filter @jornjp/adapter-node build
node examples/test-bff/server.js
```

攻撃のようなリクエストの送り方は [examples/test-bff の README](examples/test-bff/README.md#試す) にあります。
結果はブラウザの **http://localhost:3000** (ダッシュボード) で確認できます。
起動時に疑似的なリクエストが流れるため、最初から承認待ちや遮断中の IP が表示されます (不要なら `JEV_ARGOS_DEMO=false docker compose up`)。

| サービス | URL | 備考 |
| --- | --- | --- |
| ダッシュボード | http://localhost:3000 | 管理 API へのトークン付与はダッシュボードの nginx が行う |
| テスト用 BFF | http://localhost:4000 | 手順 2 で起動したもの |
| gRPC (受信) | localhost:50051 | アダプターの `target` に指定する |
| 管理 API | http://localhost:8080 | `Authorization: Bearer $JEV_ARGOS_ADMIN_TOKEN` が必須 |
| PostgreSQL | localhost:55432 | `jevargos` / `jevargos`。判定ログ `jev_decision_logs`、承認キュー `jev_actions` |

<details>
<summary>Docker Compose の補足 (LLM・Slack・停止方法など)</summary>

- LLM 分析はホストの Ollama (`http://localhost:11434`) を使う。Ollama もコンテナで動かす場合:
  ```bash
  JEV_ARGOS_OLLAMA_URL=http://ollama:11434 docker compose --profile llm up --build
  docker compose exec ollama ollama pull qwen2.5:3b   # 初回のみ
  ```
- Slack 通知は `JEV_ARGOS_SLACK_WEBHOOK_URL`、承認された対処の実行先は `JEV_ARGOS_ACTION_WEBHOOK_URL` を指定して起動する。
- 公開ポートはすべて `127.0.0.1` に限定している。ダッシュボードに到達できる人は承認操作ができるため、外部に公開する場合は前段で管理者を認証すること。
- 停止は `docker compose down` (データも消す場合は `docker compose down -v`)。

</details>

## 自分のアプリに組み込む

ここでは Express の最小例を示します。Next.js・Fastify・gRPC・Go は [ドキュメント一覧](#ドキュメント一覧) の各 README を参照してください。

**1. 判定サーバーを起動する**

```bash
# リポジトリのルートで
docker build -t jev-argos/server .
docker run -d --name jev-argos \
  -p 127.0.0.1:50051:50051 -p 127.0.0.1:8080:8080 \
  -e JEV_ARGOS_ADMIN_TOKEN=$(openssl rand -hex 16) \
  jev-argos/server

# または Go 1.26 以上で直接起動
go run ./cmd/jev-argos-server
```

50051 番 (gRPC) でリクエストの情報を受け付け、8080 番で管理 API (承認・遮断の操作) を提供します。
`JEV_ARGOS_ADMIN_TOKEN` を指定しない場合は、起動ごとに一時的なトークンが作られてログに出ます (開発用)。

**2. アダプターを入れて、ルートより前に登録する**

```bash
pnpm add @jornjp/adapter-node   # npm 公開前の入れ方は packages/adapter-node の README を参照
```

```ts
import express from "express";
import { BlocklistWatcher, SignalReporter, createExpressMiddleware } from "@jornjp/adapter-node";

const reporter = new SignalReporter({ target: "localhost:50051" });   // リクエストの情報を送る
const blocklist = new BlocklistWatcher({ target: "localhost:50051" }); // 遮断中の IP を受け取る (遮断しないなら不要)

const app = express();
app.use(createExpressMiddleware(reporter, { sourceService: "main-bff", blocklist }));

app.get("/users/:id", (req, res) => res.json({ id: req.params.id })); // 既存のルートはそのまま
```

**3. 動作を確認する**

存在しないページに 1 分間で 30 回アクセスすると、「エラーの集中」として検知されます。

```bash
# localhost:4000 はあなたのアプリのアドレスに置き換える
for i in $(seq 30); do curl -s -o /dev/null http://localhost:4000/no-such-page-$i; done
docker logs jev-argos 2>&1 | grep "jev-argos action"
```

```
msg="jev-argos action" level=3 downgraded=true score=3.6 confidence=0.625 client_ip=127.0.0.1 method="GET (unmatched)" ip_error_count_1m=30 ...
```

スコアは危険域 (3.6) ですが、エラーの集中という 1 種類の兆候だけでは確信度が足りない (0.625) ため、
自動遮断ではなく**承認キュー**に入りました (`level=3 downgraded=true`)。正常なリクエストはログに出ません。

## 他の言語で使う

公式のアダプターは Node.js と Go だけですが、アダプターと判定サーバーのやり取りは gRPC ([proto/signal.proto](proto/signal.proto)) で決まっています。
**gRPC に対応している言語 (Java / Kotlin・C#・Python・Ruby・Rust など) なら、アダプターを書けば検知と遮断の両方が使えます。**
規模の目安は、gRPC だけなら 300〜450 行、HTTP のミドルウェアも入れると 400〜600 行です。

| 使う RPC | 用途 |
| --- | --- |
| `SignalService.ReportSignal` (バッチなら `StreamSignals`) | リクエストの情報を送る |
| `ControlService.WatchBlocklist` (サーバー側のストリーミング) | 遮断中の送信元の一覧を受け取る |

アダプターが守るべきことのうち、特に重要なのは次の 4 つです。

- **送信はアプリを待たせない**: 非同期で送り、あふれたら捨て、例外をアプリに投げない
- **`status_code` は gRPC のコード**: HTTP の 403 は 7 (`PERMISSION_DENIED`) に変換する。権限の探索の検知に使うため
- **`method` は API ごとに同じ文字列**: HTTP なら実際の URL ではなく `GET /users/:id` のようなルートのパターン。どのルートにも合わなければ `GET (unmatched)`
- **遮断の判定は手元のコピーで行う**: 遮断リストのストリームが切れたら自動で再接続し、その間は最後に受け取った一覧で判定を続ける

詳細 (フィールドごとの値・ステータスの変換表・再接続の決まり・動作確認のチェックリスト) は [docs/adapter_spec.md](docs/adapter_spec.md) にあります。

> 遮断リストを購読するため、プロセスが常駐している必要があります。PHP-FPM のようにリクエストごとにプロセスが終わる環境では、常駐の実行環境かサイドカーが必要です。
> 検知だけなら、gRPC を使わずに HTTP の `POST /api/signals` でも送れます ([判定サーバーの README](cmd/jev-argos-server/README.md#api))。

## 実装状況と既知の制約

| 項目 | 現状 |
| --- | --- |
| **Jev モデル** | 学習データが無いため、学習済みモデルの代わりにルールベースの暫定モデルで動いている。`classifier.Model` を実装すれば差し替えられる |
| **LLM 分析の精度** | 使う LLM に依存する。既定の `qwen2.5:3b` は軽さ優先なので、精度が必要なら大きいモデルや Claude を使う。LLM が提案できる対処は取り消せるもの (IP 遮断・セッション無効化・アカウント一時停止・縮小運転) に限り、すべて承認キューを通る |
| **遮断以外の対処の実行** | セッション無効化・アカウント操作・データ削除・縮小運転・サービス停止は、アプリが受信エンドポイント (`JEV_ARGOS_ACTION_WEBHOOK_URL`) を用意して実行する。jev-argos は署名付きで依頼するだけ |
| **複数台構成** | Redis (統計・遮断リスト) と PostgreSQL (承認キュー) を使うと複数台で共有される。指定しない場合はメモリ上にあり、再起動で消える。受信と判定だけを行う receiver と、後続処理を行う worker に分けて、receiver だけを台数で増やすこともできる ([判定と後続処理を分ける](cmd/jev-argos-server/README.md#判定と後続処理を分ける-receiver--worker)) |
| **通信の暗号化と認証** | gRPC・管理 API とも TLS は内蔵していない。管理 API は共有トークン方式で、承認者名は自己申告。本番ではサービスメッシュやリバースプロキシで TLS と管理者の認証を行う |
| **パッケージの公開** | Docker イメージ・npm パッケージとも未公開 (ローカルでビルドして使う)。Go のパッケージは `go get github.com/jornJp0201/jev-argos/pkg/client` で取得できる |
| **性能検証** | 判定サーバー内の処理はベンチマークで測定済み ([改善したポイント](#改善したポイント))。設計書 9 章の性能検証 (ネットワークを含む判定までのレイテンシ、LLM 単体との比較) は未実施 |

## 改善したポイント

### ダッシュボードへの配信が、判定のコストの 95% を占めていた

**課題**

判定サーバーは、全リクエストの判定結果をダッシュボードにリアルタイムで配信しています。
この配信処理は判定のたびに同期的に呼ばれるため、遅いとそのまま全リクエストの判定が遅くなります。
ベンチマークを取ると、判定そのもの (バッファ → Jev → ガードレール) は **約 0.21µs** なのに、配信を含めると **約 4.8µs** かかっていました。判定のコストの約 95% が配信だったことになります。

**原因**

- 判定 1 件ごとに、シグナルを 2 段階で JSON に変換していた (1 件あたりメモリ確保 48 回・約 3KB)
- ダッシュボードを誰も開いていなくても、毎回変換していた
- 判定の大半を占める正常なリクエスト (Level 1) も、1 件ずつ変換して送っていた
- 直近分の保持に配列を使っていて、上限に達すると追加のたびに全体をコピーしていた
- すべての判定が 1 つのロックを取るため、並列のリクエストがそこで待たされていた

**対策** (`pkg/events/hub.go`)

1. **Level 1 は 1 件ずつ送らず、1 秒ごとの件数にまとめる**: ロックを取らないカウンター (`atomic`) で件数とスコアの合計だけを数え、1 秒ごとに 1 通の `summary` として配信する
2. **購読者がいなければ JSON にしない**: Level 2 以上の判定は、変換せずにそのまま直近分として持つ。ダッシュボードが接続したときに初めて変換する
3. **直近分をリングバッファにする**: 上限に達しても古い要素を上書きするだけにし、コピーをなくす

**結果** (Apple M2 / Go 1.27、`go test -run '^$' -bench . -benchmem ./pkg/events/`)

| 測定項目 | 改善前 | 改善後 |
| --- | --- | --- |
| 判定 1 回 (配信を含む) | 4,800 ns・確保 48 回 | **221 ns・確保 0 回** (約 22 倍速) |
| Level 1 の配信 (ダッシュボードなし) | 4,640 ns・確保 48 回 | **10 ns・確保 0 回** |
| Level 1 の配信 (ダッシュボードあり) | 6,330 ns | **10 ns** |
| Level 1 の配信 (8 並列) | 2,430 ns | **74 ns** (約 33 倍速) |
| Level 3 の配信 (ダッシュボードなし) | 4,640 ns | **25 ns** |
| Level 3 の配信 (ダッシュボードあり) | 6,330 ns | 5,990 ns (変換が必要なため変わらない) |

配信のコストが判定より小さくなり、判定サーバー内では判定そのものが律速になりました。

副次的な効果として、ダッシュボードの概況も正確になりました。
これまではブラウザが保持する直近 2,000 件の大半が Level 1 で埋まり、毎秒 1,000 件の環境では 2 秒分しか残らず、「直近 5 分」の集計が成り立っていませんでした。
今は Level 1 が 1 秒 1 通にまとまるので、5 分間の件数を正しく出せます。また、警戒すべき Level 2 以上の判定が Level 1 に押し出されることもなくなりました。

**トレードオフ**

- ダッシュボードのシグナル一覧には Level 1 が出なくなった (件数は概況に出る)。Level 1 の個々の判定は、もともと判定ログにも保存していない
- Redis を使う構成では Redis との通信が判定の時間の大半を占めるため、改善の比率はメモリ構成より小さくなる (Redis 側の改善は次の項目)

### Redis への往復が 1 シグナルあたり 4 回あり、1 つのキーに書き込みが集中していた

**課題**

複数台構成では、送信元ごとの統計を Redis で共有しています。
1 件のシグナルを判定するのに Redis へ **4 回往復**していて、判定の時間のほとんどが通信待ちでした (1 件あたり約 0.9〜1.1ms)。
さらに、API ごとの「普段の処理時間」(レイテンシの基準値) を全 API で 1 つのキーに入れていて、**正常なリクエストのたびに全インスタンスがこのキーを更新**していました。
Redis Cluster でノードを増やしても、このキーだけは 1 つのノードに載るため、そこに負荷が集中して台数を増やす効果が出ません。

**原因**

- 判定の手順 (基準値の取得 → 記録 → 1 分の集計 → 5 分の集計) が、インターフェースのメソッドを 1 つずつ呼ぶ作りで、それぞれが Redis への 1 往復になっていた
- 基準値の更新を、リクエストのたびに Redis 上で行っていた

**対策** (`pkg/buffer/redis_buffer.go`)

1. **往復を 1 回にまとめる**: 記録と 2 つの集計を 1 つのパイプライン (異常応答のときは MULTI/EXEC) で送る。同じ送信元のキーは同じスロットに置いているので、Redis Cluster でも 1 回で済む。`Buffer` インターフェースは変えず、まとめて処理できる実装だけが任意の `SignalObserver` を実装する形にして、差し替えポイントの互換性を保った
2. **基準値は各インスタンスのメモリで計算し、5 秒ごとに Redis とすり合わせる**: 各インスタンスは手元の基準値で判定し、その間に観測した「平均と件数」を 5 秒ごとに Lua スクリプトで送り、全体の基準値を受け取る (これも 1 往復)。n 件の観測は、移動平均 (EWMA) を n 回適用したときと同じ重み `1-(1-α)^n` で全体に混ぜる。すり合わせに失敗した観測は捨てずに次回に送る

**結果** (Apple M2、Docker の Redis 7.4、`JEV_ARGOS_TEST_REDIS_URL=... go test -run '^$' -bench Redis -benchmem ./pkg/buffer/`)

| 測定項目 | 改善前 | 改善後 |
| --- | --- | --- |
| Redis への往復 (1 シグナルあたり) | 4 回 | **1 回** |
| 判定 1 回 (正常な応答、3 回の中央値) | 約 880 µs | **約 213 µs** (約 4 倍速) |
| 判定 1 回 (権限エラー、6 回の中央値) | 約 1,060 µs | **約 280 µs** (約 3.8 倍速) |
| 並列のスループット (64 並列、1 割が権限エラー) | 約 9,700 件/秒 (約 104 µs/件) | **約 39,000 件/秒** (約 26 µs/件、約 4 倍) |
| レイテンシの基準値のキーへの書き込み | 正常なリクエストごとに 1 回 | **インスタンスごとに 5 秒に 1 回** |

往復の回数は、go-redis のフックで数えたものです (`TestRedisBuffer_ObserveIsOneRoundTrip` でも確認している)。
時間は Mac 上の Docker を経由した値で、同じデータセンター内の Redis なら往復 1 回の時間はもっと短くなります。ただ、往復の回数が 1/4 になる効果はどの環境でも変わりません。

**トレードオフ**

- インスタンス間で基準値がずれるのは、最大でもすり合わせの間隔 (既定 5 秒、`RedisOptions.LatencySyncInterval`) の分だけ。基準値は移動平均でゆっくり動く値なので、判定への影響は小さい
- 起動直後のインスタンスは、最初のすり合わせ (起動時に実行) で全体の基準値を受け取るまで、比率を 1.0 として扱う

### 攻撃を受けるほど DB への書き込みが増えていた

**課題**

攻撃者からのリクエストは連続して Level 3 (攻撃の疑い) になります。
これまでは 1 件ごとに、承認キューへの提案 (件数の確認・upsert・他インスタンスへの通知を 1 トランザクションで、**SQL 5 回・約 1.3ms**) と、判定ログの INSERT (**SQL 1 回・約 0.4ms**) を実行していました。
つまり、**攻撃を受けるほど DB が重くなる**作りでした。

さらに、これらは判定の後続処理を担う 4 つのワーカーの中で行われ、自動遮断 (Level 4) も同じキューに並んでいます。
計算上は、毎秒約 2,300 件の Level 3 (1.7ms × 4 ワーカー) でキューがあふれます。あふれると、肝心の自動遮断のイベントまで捨てられてしまいます。

**原因**

- 承認キューは「同じ送信元への承認待ちは 1 件にまとめる」ようになっていたが、まとめる処理を DB 側で 1 件ごとに行っていた
- 判定ログを 1 件ずつ INSERT していた

**対策**

1. **承認キューへの提案は、送信元ごとに 2 秒まとめる** (`pkg/approval` の `ProposeEmitter.Window`)
   - ある送信元からの最初の提案だけはすぐに書く (管理者がすぐに気付けるように)
   - その後の 2 秒間に続いた提案はメモリ上で件数を合算し、根拠は最新のものだけを残して、2 秒ごとに 1 回だけ書く
   - 攻撃が止まった送信元は、次の提案をまたすぐに書く
   - まとめる送信元の数には上限 (既定 1 万) があり、超えた分は従来どおり 1 件ずつ書く (分散型の攻撃でメモリを使い切らないように)
2. **判定ログはまとめて書く** (`pkg/db` の `BatchWriter`)
   - 保存はキューに積むだけにして、500 件たまるか 0.5 秒経つたびに 1 回の SQL で保存する
   - PostgreSQL は列ごとの配列を `unnest` で行に戻す `INSERT ... SELECT` にした (`COPY` は再送の重複を無視する `ON CONFLICT` を使えないため)。SQLite は 1 トランザクションにまとめる
3. **まとめたことで壊れる箇所への対処**
   - LLM 分析は判定ログの行を更新するため、分析を保存する前に、保存待ちの判定ログを先に書き出す
   - 同じ SQL でまとめて保存すると保存時刻 (`received_at`) がすべて同じになり、LLM に渡す履歴の新しい順が崩れる。そこで、判定した時刻を記録して保存するようにした
   - 停止時は、判定の処理を止めた後に、まとめている提案と判定ログを書き出してから終了する

**結果** (Apple M2、Docker の PostgreSQL 16、`JEV_ARGOS_TEST_POSTGRES_URL=... go test -run '^$' -bench . -benchmem ./pkg/approval/ ./pkg/db/`)

| 測定項目 (攻撃中、Level 3 が続く) | 改善前 | 改善後 |
| --- | --- | --- |
| 承認キューへの提案 (1 件あたりのワーカーの時間) | 約 1,300 µs・SQL 5 回 | **約 0.11 µs**・SQL は送信元ごとに 2 秒に 2 回 |
| 判定ログの保存 (1 件あたり、保存完了まで) | 約 400 µs・SQL 1 回 | **約 4 µs** (約 100 倍)・SQL は約 500 件に 1 回 |

攻撃を受けても DB への書き込みはほとんど増えなくなり、ワーカーが詰まって自動遮断が捨てられる心配も小さくなりました (自動遮断と遅い処理が同じキューに並ぶ問題自体は、次の項目で解消しています)。

実際のサーバーに、同じ送信元から権限エラーを 200 件送って確認しました。Level 3 は 11 件で、承認キューには最初の 1 件がすぐに入り、残りの 10 件は合算され、件数は 11 件と一致しました。判定ログも、停止時にすべて保存されていました。

**トレードオフ**

- 承認待ちの件数と根拠が画面に反映されるのは、最大 2 秒遅れる (新しい送信元の最初の提案は遅れない)
- 判定ログが DB に入るのは、最大 0.5 秒遅れる
- プロセスが強制終了 (`kill -9` など) された場合は、まとめている途中の件数 (最大 2 秒分) と判定ログ (最大 0.5 秒分) が失われる。通常の停止では書き出してから終了する
- 判定ログの保存待ちがあふれた場合 (既定 1 万件) は捨て、捨てた件数を警告として出す。判定と遮断には影響しない

### 高負荷のときほど自動遮断が捨てられていた

**課題**

Level 2 以上の判定の後続処理 (ログ・自動遮断・承認キュー・判定ログ・Slack 通知・LLM 分析) は、1 つのキューを 4 つのワーカーが取り出し、1 件ずつ順番に処理していました。
このため、**どれか 1 つが遅いとキュー全体が詰まります**。たとえば Slack の応答が遅い (1 件 200ms) だけで、処理できるのは毎秒 20 件 × 4 ワーカーになります。
キューがあふれると、新しいイベントはまとめて捨てられます。その中には **Level 4 の自動遮断も含まれます**。
攻撃が激しいほど遮断が必要なのに、攻撃が激しいほど遮断されない、という逆転が起きていました。

**原因**

- 速さも重要度も違う処理が、1 つのキューを共有していた
- キューに積むかどうかを処理ごとに判断していなかった。自動遮断に関係ない Level 2・3 のイベントでもキューが埋まっていた

**対策** (`pkg/receiver` の `Lane`)

1. **後続処理ごとに専用のキューとワーカーを持たせる** (`receiver.Options.Lanes`)
   - 遮断 (`block`)・承認キュー (`approval`)・ログ (`log`)・判定ログと LLM 分析 (`persist`)・通知 (`notify`) の 5 つに分けた
   - 判定は、各キューに待たずに積むだけにした。あるキューが満杯でも、そのキューの分だけを捨てる。他のキューと、判定の応答には影響しない
2. **キューごとに、受け付ける Level を決める** (`Lane.MinLevel`)
   - 遮断のキューには Level 4 だけが入る。Level 2・3 がどれだけ来ても、遮断のキューは埋まらない
3. **処理の速さに合わせてワーカー数を変える**: 外部への HTTP 呼び出しをする通知は 4、遮断は 2、メモリ上で済むものは 1
4. **順序が必要なものは同じキューに入れる**: LLM 分析は判定ログの行を更新するため、判定ログと LLM 分析は同じキュー (`persist`) で、判定ログを先に渡す (どちらもキューに積むだけなので遅くならない)
5. **捨てたイベントの数は、キューごとに数える** (`Server.DroppedByLane`)。警告はキューごとに 1 秒に 1 回までにして、攻撃中にログがあふれないようにした

ライブラリとしての互換性は保っています。`NewServer` に `Emitter` を 1 つ渡す従来の使い方も、そのまま動きます (内部では `default` という Lane が 1 つあるのと同じ)。

**結果** (Apple M2、`go test -run '^$' -bench SlowNotifier -benchtime 1x ./pkg/receiver/`)

攻撃中を想定して、Level 3 と Level 4 を 9:1 で毎秒 5,000 件 (送信元はすべて別) を 2 秒間送り、Slack 通知に 1 件 200ms かかる場合を測りました。

| 測定項目 | 改善前 (1 つのキュー) | 改善後 (処理ごとのキュー) |
| --- | --- | --- |
| Level 4 のうち、自動遮断されたもの | **10.4%** | **100%** |
| 自動遮断までの遅れ (p99) | 約 50 秒 (通知待ちのキューに並ぶため) | **約 0.02 ms** |

通知がどれだけ遅れても、自動遮断は判定の直後に行われるようになりました。

**トレードオフ**

- キューの数だけメモリを使う。キューの 1 枠は 64 バイトで、シグナル本体はキュー間で共有する。既定の 1,024 件 × 5 キューで約 320KB
- 通知のキューがあふれると、通知は捨てられる (これまでも同じ)。その場合も、判定ログ・承認キュー・ダッシュボードには残る
- キューが分かれたため、処理ごとの完了の順序は保証されない (例: 通知が判定ログの保存より先に届くことがある)。順序が必要な組み合わせは、同じキューに入れる

### 正常な応答まで 1 件ずつ送っていた

**課題**

アダプターは、BFF へのすべてのリクエストを 1 件ずつ判定サーバーに送っていました。判定サーバーの受信量は、BFF のリクエスト数そのものです。
ところが、リクエストの大半を占める正常な応答は、サーバー側では **API ごとの普段の処理時間 (レイテンシの基準値) の計算にしか使われていません**。
攻撃の判定に使う統計 (1 分間のエラー数・5 分間に権限エラーを起こした API の数) は、エラーだけから数えています。

**原因**

- 送るかどうかを、応答の種類によらず一律に決めていた
- サーバーが「1 件 = 1 件」として数える作りだったため、間引くとレイテンシの基準値と件数がずれる

単純に間引くだけでは解決しません。処理時間の急増を見逃さないよう、遅い応答は必ず送る必要があります。
しかし、遅い応答だけを多めに送ると、サーバーからは遅い応答の割合が実際より多く見えます。その結果、**基準値が実際より高くなり、急増を見逃します**。

**対策**

1. **アダプターで正常な応答を間引く** (Go: `ReporterOptions.Sampling`、Node.js: `sampling`)
   - エラーはすべて送る
   - 遅い応答は必ず送る。遅いかどうかは、アダプターの手元で API ごとに求めた平均と比べる (既定は 2 倍超)。固定の閾値も指定できる
   - それ以外の正常な応答は、指定した割合 (例: 10%) だけ送る
   - ライブラリの既定は「全件送る」のままにし、設定で有効にする (使う側が知らないうちに送る量が変わらないように)。付属のサンプル BFF は 10% にした
2. **送った割合をシグナルに載せる** (`SecuritySignal.sample_rate`)
   - 間引いて送った正常な応答には `sample_rate` (例: 0.1) を付ける。必ず送ったものには付けない
   - 未指定は「全件送った」として扱うので、古いアダプターもそのまま動く
3. **サーバーは 1/sample_rate 件ぶんとして数える**
   - レイテンシの基準値: 10 件ぶんの観測として、移動平均 (EWMA) を 10 回適用したときと同じ重み `1-(1-α)^10` で混ぜる。Redis とのすり合わせでも件数を重みとして送る
   - ダッシュボードの Level 1 の件数とスコアの合計も、重みを掛けて数える
   - 1 件が表せる件数は最大 100 件ぶん (sample_rate 0.01) までにし、極端な値で基準値が大きく動かないようにした

**結果** (`go test -run SamplingAccuracy -v ./pkg/client/`)

1 つの API への正常な応答 20 万件で測りました。処理時間は普段は平均 50ms でばらつき、3% は処理時間の急増 (150〜250ms) とします。これを判定サーバーと同じ部品 (バッファ → Jev → ガードレール) に通しています。

| 送り方 | 送った件数 | 基準値の誤差 (平均) | 急増の検知 (Level 2 以上) |
| --- | --- | --- | --- |
| 全件 (改善前) | 200,000 件 (100%) | 5.4 ms | 3,693 件 (基準) |
| 25% (重み付き) | 54,173 件 (27.1%) | 7.6 ms | 3,463 件 (93.8%) |
| **10% (重み付き)** | **25,305 件 (12.7%)** | 10.8 ms | **3,268 件 (88.5%)** |
| 10% (重みなし、`sample_rate` を付けない場合) | 25,305 件 (12.7%) | 30.3 ms | 250 件 (6.8%) |

10% では、判定サーバーの受信量が **約 1/8** になりました (遅い応答と、初めて見る API の最初の応答は必ず送るため、ちょうど 1/10 にはならない)。
エラーはすべて送るので、攻撃の判定に使う統計は全件のときと変わりません。
重みを付けないと、基準値が実際より高くずれて、急増の 9 割以上を見逃します。サーバー側の重み付けが必要なことも確認できました。

**トレードオフ**

- 間引くほど、レイテンシの基準値のばらつきが大きくなる。10% では急増の検知が全件のときの約 9 割になり、正常な応答 20 万件中 11 件 (0.006%) を誤って Level 2 と判定した。精度を優先するなら割合を上げる (25% なら約 94%、誤検知 0 件)
- 間引いた応答には判定が返らないため、`OnResponse` / `onResponse` は呼ばれない。攻撃者はエラーで検知され、遮断は遮断リストで配信されるので、遮断には影響しない
- 流量の少ない API は、届く件数が減るぶん基準値が安定するまで時間がかかる

### 判定サーバーが後続処理まで抱えていて、台数で増やしにくかった

**課題**

判定サーバーは、受信と判定に加えて、後続処理 (承認キュー・判定ログ・LLM 分析・通知) とダッシュボードへの配信まで 1 つのプロセスで行っていました。
受信量が増えたときに増やしたいのは受信と判定の部分だけです。それでも、増やすと後続処理も一緒に増えてしまいます。
また、後続処理のキューはプロセスのメモリ上にあります。そのため、通知などが遅れて詰まると、**あふれた分は捨てるしかありませんでした**。プロセスが落ちれば、キューに残っていた分も失われます。

**原因**

- 速く・軽く・状態を持たない処理 (受信と判定) と、遅く・外部に依存する処理 (DB・通知・LLM) が、同じプロセスにあった
- 2 つの間の受け渡しが、プロセス内のキューだった

**対策** (`pkg/stream`、`JEV_ARGOS_ROLE`)

1. **プロセスの役割を 2 つに分けられるようにした**
   - `receiver`: 受信・判定・自動遮断だけを行う。統計と遮断リストは Redis にあるため状態を持たず、台数で増やせる
   - `worker`: 承認キュー・判定ログ・LLM 分析・通知、ダッシュボードへの配信を行う
   - 既定 (`all`) はこれまでどおり 1 プロセスで動く。Redis を使わない手軽な構成も残した
2. **判定結果を Redis Streams で受け渡す**
   - Redis は既に使っているので、Kafka などを新しく入れずに済む
   - receiver は Level 2 以上の判定を、まとめて 1 回の往復で `XADD` する
   - Level 1 は 1 件ずつ流さず、receiver ごとに 1 秒 1 件の件数 (summary) にまとめる (1 つ目の改善と同じ考え方)
3. **後続処理ごとに consumer group を作る** (`approval` / `persist` / `notify`)
   - group ごとに読む位置が別なので、どれかが遅れても他は止まらない (4 つ目の改善と同じ考え方)
   - 遅れた分は Redis に残り、捨てられずに後から処理される
   - worker を増やすと、同じ group の Consumer 同士で判定を分け合う
4. **落ちても失わない**
   - 判定は後続処理に渡し終えてから処理済み (`XACK`) にする。判定ログは DB に書いてから処理済みにする
   - 処理済みにしないまま worker が落ちた場合、その判定は 30 秒後に他の worker が引き取る (`XAUTOCLAIM`)
5. **自動遮断は receiver で行う**
   - 最優先の処理なので、worker を経由させず、判定の直後に行う
6. **ダッシュボードは worker に向ける**
   - 各 worker は consumer group を使わずにストリームを読み、すべての判定と、全 receiver の Level 1 の件数を受け取って配信する

**結果** (Apple M2、Docker の Redis 7.4、`JEV_ARGOS_TEST_REDIS_URL=... go test -run '^$' -bench . -benchtime 1x ./pkg/stream/`)

攻撃中を想定して、Level 3 を毎秒 2,500 件、2 秒間流しました。送信元はすべて別で、通知は 1 件 10ms かかるとします。

| 測定項目 | 改善前 (プロセス内のキュー) | 改善後 (Redis Streams) |
| --- | --- | --- |
| 通知まで届いた判定 | **36.3%** (残りはあふれて捨てた) | **100%** |
| すべて処理し終えるまで | 4.8 秒 | 14.1 秒 (遅れた分を後から処理) |
| receiver からストリームへの追加 | — | 約 28 万件/秒 (3 回の中央値) |

実際に、Redis 1 台・receiver 2 台・worker 1 台で動かしても確認しました。
- 同じ送信元からの権限エラーを 2 台の receiver に交互に送ったところ、統計は Redis で共有されるので、どちらの receiver でも Level 4 になり、自動遮断された
- worker には、Level 2 以上の 39 件がすべて届いた。判定ログに 39 件が保存され、承認キューにも入り、ダッシュボードにも配信された
- ダッシュボードの Level 1 の件数は、両方の receiver の合計 (1,001 件) と一致した

**トレードオフ**

- 構成要素が増える。receiver と worker を分けると、Redis が必須になる (既定の 1 プロセス構成なら不要)
- 同じ判定が 2 回処理されることがある (at-least-once)。worker が処理済みにする前に落ちた場合や、処理済みにする操作が失敗した場合。判定ログは `signal_id` で重複を除き、通知と LLM 分析は送信元ごとに間引くため、影響は小さい。承認キューの件数は多めに数えることがある
- 承認キューへの提案は 2 秒まとめてから書くため、まとめている途中で worker が強制終了すると、その分の件数が失われる (3 つ目の改善と同じ)
- ストリームに残すのは約 10 万件まで (`DefaultMaxLen`)。後続処理がそれ以上遅れると、古いものから消える
- 新しく作った consumer group は、作った後に追加された判定から読む (過去の判定をさかのぼって通知しないように)

### 過負荷のときに、攻撃の兆候まで後回しになっていた

**課題**

判定サーバーは、届いたシグナルを上限なく受け付けていました。
処理能力を超える量が届くと、Redis への問い合わせ待ちの列が伸び続けます。その結果、**すべてのシグナルの判定が遅れます**。
攻撃者が大量の正常なリクエストを送れば、本当に見たい攻撃の兆候 (権限エラーなど) の判定まで、その列の後ろで待たされます。
また、キューから捨てた件数は `Dropped()` でプロセスの中から見えるだけで、運用中に気付く手段がありませんでした。

**原因**

- 受け付ける量に上限がなかった (同時に判定する数・アダプターごとの量・gRPC のメッセージサイズ)
- 断る場合も、シグナルの種類を区別していなかった。正常な応答は大半が Level 1 で、サーバーでは基準値と件数にしか使わない。攻撃の判定に使うのはエラーのシグナルだけ
- 件数を外から見る口がなかった

**対策**

1. **gRPC に上限を付ける**: 1 接続あたりの同時ストリーム数 (既定 1,000) と、メッセージ 1 件の最大サイズ (既定 64KB、gRPC の既定は 4MB) を決めた
2. **同時に判定する数に上限を付け、正常な応答から先に断る** (`receiver.Limits.MaxInFlight`、既定 4,096)
   - 判定中の数が上限の 8 割を超えたら、正常な応答のシグナルを断る
   - 残りの 2 割はエラーのシグナルのために空けておき、上限に達するまで受け付ける
   - 断るのは統計に記録する前なので、断ったシグナルは Redis への問い合わせも行わない
3. **アダプター (接続元の IP) ごとに流量を制限する** (`receiver.Limits.AdapterRate`、既定 毎秒 1 万件)
   - トークンバケットの枠が半分を切ったら、正常な応答のシグナルを断る。残りの半分はエラーに使う
   - 覚えておくアダプターの数には上限 (1 万) があり、送ってこなくなったものから忘れる
4. **断ったシグナルは `RESOURCE_EXHAUSTED` (HTTP では 429) で返す**: アダプターは再送しない (再送すると負荷がさらに増える)
5. **メトリクスを出す** (`GET /metrics`、Prometheus 形式、`pkg/metrics`)
   - 判定数 (Level ごと)、断った数 (理由と、正常な応答かエラーか)、判定中の数、キューごとの捨てた数、worker の遅れ (consumer group ごと) を出す
   - 外部のライブラリには依存せず、テキスト形式を直接書き出す

**結果** (Apple M2、`go test -run '^$' -bench Overload -benchtime 1x ./pkg/receiver/`、3 回の中央値)

Redis の接続数と往復時間を模して、バッファは同時に 32 件まで、1 件 1ms とします。処理能力は毎秒 32,000 件です。
そこに毎秒 48,000 件 (処理能力の 1.5 倍) の正常なシグナルを 2 秒間流し、攻撃者の権限エラー (毎秒 100 件) が判定されるまでの時間を測りました。

| 測定項目 | 上限なし (改善前) | 上限あり・優先なし | **上限あり・正常な応答から断る (改善後)** |
| --- | --- | --- | --- |
| 攻撃のシグナルの判定までの時間 (p99) | 約 1,185 ms | 約 2.0 ms | **約 1.8 ms** |
| 攻撃のシグナルを受け付けた割合 | 100% | 約 66% | **100%** |
| 正常なシグナルを断った割合 | 0% | 約 34% | 約 34% |

上限がないと、判定の遅れは過負荷が続く限り伸び続けます (2 秒間で約 1.2 秒)。
上限を付けるだけでは、攻撃のシグナルも 3 件に 1 件が断られます。正常な応答から先に断ることで、攻撃のシグナルは 1 件も断らずに、遅れを 1/600 以下にできました。
受け付けの判断そのものにかかる時間は約 0.2µs で、判定 1 回の Redis の往復 (約 200µs) と比べて無視できます。

実際のサーバーでも確認しました。
- 100KB のシグナルは `RESOURCE_EXHAUSTED` で断られた
- 流量制限を毎秒 20 件にして、正常な応答とエラーを交互に 60 件送ったところ、枠 20 件のうち 14 件はエラーに使われた (正常な応答は 6 件)
- `/metrics` に、断った数が理由と種類ごとに出た

**トレードオフ**

- 過負荷のときは、正常な応答のシグナルを断るぶん、レイテンシの基準値とダッシュボードの Level 1 の件数が実際より少なく見積もられる。断った数は `jevargos_signals_rejected_total` で分かる
- 正常な応答でも、攻撃者の IP からのものは Level 2 以上になることがある。過負荷のときはこれも断るが、同じ IP のエラーは受け付けるので、判定への影響は小さい
- アダプターの識別は接続元の IP で行う。1 つの IP の後ろに多数の BFF がある場合 (NAT 等) は、まとめて制限されるので `JEV_ARGOS_ADAPTER_RATE` を上げる
- 既定の上限値 (同時 4,096・毎秒 1 万件) は余裕を持たせた初期値で、実測で決めたものではない。メトリクスを見て調整する
- `/metrics` は認証なしで公開する (件数だけで機密情報を含まないため。`/api/healthz` と同じ)。外部に公開しないネットワークに置く
